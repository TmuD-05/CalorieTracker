2. System Boundaries & Data Flow Architecture

The system is organized into 5 decoupled boundaries that transition data safely from physical hardware sensors to cloud foundation models:

  • Boundary 1 (Hardware Sensor → OS): User taps "Capture Meal". Browser issues an OS-level intent via capture="environment", delegating execution to the native camera application (activating OIS, macro/wide optical switching, and flash).
  • Boundary 2 (In-Browser Edge Transform): Raw multi-megabyte photo is decoded asynchronously off the UI thread via createImageBitmap(), clamped to max 2048px, stripped of EXIF metadata on an OffscreenCanvas, and compressed to WebP (~350KB).
  • Boundary 3 (Local Persistence / Outbox): Downscaled blob and meal draft are committed into IndexedDB (Dexie.js) with status PENDING_UPLOAD and a client-generated UUIDv7.
  • Boundary 4 (Ingestion Gateway): The client streams the 350KB payload to Django Ninja (POST /api/food/analyze-food) via multipart/form-data with memory validation.
  • Boundary 5 (Foundation Model): The backend forwards the byte stream to Gemini 3.6 Flash via types.Part.from_bytes(), enforcing typed Pydantic schema decoding.

4. Deep Dive 1: Why Client-Side Edge Transformation?

The Problem: Cellular Uplink Saturation & Server Swap Depletion

Modern smartphones produce 12MP to 48MP photos (8MB to 15MB HEIC/JPEG files). Uploading these directly causes two severe failure modes:

  1. Cellular Uplink Throttling: Mobile cellular networks are heavily asymmetrical. While download speeds are fast, mobile uplink speeds are often limited to 2–5 Mbps in real-world scenarios. Uploading an uncompressed 15MB file takes 8 to 15 seconds of radio transmission, creating high friction for the user.
  2. Server Memory Exhaustion: If 1,000 concurrent mobile users upload uncompressed 15MB photos simultaneously, the server must buffer: 
    1,000 users × 15 MB = 15 GB of raw network buffers
    This causes server processes to exhaust available RAM, forcing the operating system into disk swapping, which balloons API latency from milliseconds to tens of seconds and causes Out-Of-Memory (OOM) worker restarts.

The Client Transform Solution

By executing proportional downscaling and WebP compression on the client before the network request is opened:

  • Payload Reduction: File size is reduced from 12MB to ~350KB (a 97% reduction).
  • Transmission Latency: Upload finishes in < 300ms on mobile connections.
  • Server Predictability: The Django server handles lightweight, predictable payloads that fit cleanly into memory buffers without swap saturation.

Why 2048px is the Gemini Vision "Sweet Spot"

Multimodal vision foundation models process images by segmenting them into fixed-dimension pixel patches. Images above 2048px are downsampled by the model's pre-processor anyway. Clamping the maximum dimension to 2048px preserves fine-grained food textures (such as grains of rice, sauce viscosity, and spices) without transmitting redundant pixels.

Privacy by Design: EXIF & GPS Scrubbing

When an image file is drawn onto an HTML5 <canvas>, the browser extracts only the raw color raster. All auxiliary metadata tags—including precise GPS location coordinates, camera serial numbers, and device fingerprints—are permanently stripped on the user's device before any bytes leave over the network.

5. Deep Dive 2: Wire Protocol & API Request Sizing

Ingestion Wire Protocol (POST /api/food/analyze-food)

The client does not transmit Base64 JSON strings. It sends standard binary multipart/form-data:

POST /api/food/analyze-food HTTP/1.1
Host: api.calorietracker.local
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW
X-Client-Request-Id: 0191c95e-3990-7d72-9a3b-2802bcfb17ce
Content-Length: 358412

------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="image"; filename="meal_0191c95e.webp"
Content-Type: image/webp

<binary WebP stream: 350,120 bytes>
------WebKitFormBoundary7MA4YWxkTrZu0gW--

Backend Ingestion Guards (Django Ninja)

  • Size Limit Enforcement: In api/endpoints.py, files over 25MB are immediately rejected with HTTP 413 Payload Too Large before reading the body into server memory.
  • MIME Gate: Only content types matching image/* are accepted.
  • Zero-Swap Streaming: image.read() passes the in-memory 350KB buffer directly to types.Part.from_bytes(). No temporary files are written to the host filesystem.

6. Deep Dive 3: Memory Pointer Lifecycles & Mobile WebKit RAM Constraints

The Mobile Browser Memory Ceiling: On iOS Safari (WebKit), tabs that consume more than approximately 300MB–400MB of RAM are aggressively killed by the operating system (SIGKILL), reloading the page and destroying application state.

The Uncompressed Raster Math

A full-resolution 48MP photo contains 48,000,000 pixels:

48,000,000 pixels × 4 bytes (RGBA) ≈ 192 MB of uncompressed RAM

If an application reads the file via FileReader.readAsDataURL() (Base64 string) and decodes it without cleanup, memory usage immediately surges past 240MB from a single photo, triggering tab crashes.

Zero-Memory-Leak Rules Implemented

Rule Dangerous Pattern Our Architectural Implementation
1. Avoid Base64 readAsDataURL(): +33% memory bloat, duplicates string in V8 heap. createImageBitmap(): Decodes off the main UI thread directly into native GPU memory.
2. Explicit Handle Teardown Relying on JS garbage collection for native graphics handles. bitmap.close() in a finally block releases GPU memory immediately.
3. Canvas Backing Store Release Leaving canvas dimensions intact after drawing. canvas.width = 0; canvas.height = 0; instructs the compositor to free the raster buffer.
4. Object URL Lifecycle Creating URL.createObjectURL() without releasing it. Every preview returns a scoped revokePreview() handle called in useEffect cleanup and on photo resets.

7. Deep Dive 4: Error State Machine & Resilient Offline Sync

Mobile networks drop connections frequently. The architecture implements a robust state machine across client and backend:

Trigger / Error Classification System Response
Offline Disconnect (No Network) Transient Network Optimistic UI: Meal saved locally in IndexedDB with status PENDING_UPLOAD. Outbox queue auto-drains when window.ononline or visibilitychange fires.
HTTP 503 / 504 (Server Overloaded) Transient Server Draft remains in outbox; retry_count increments with backoff.
HTTP 413 (File > 25MB) Permanent Client Removed from outbox; displays "Image exceeds size limit" to user.
Duplicate Sync Request Idempotency Backend checks client_request_id (UUIDv7) in MealLog. Returns existing record without duplicate calorie logging.
